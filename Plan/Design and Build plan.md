**Scope of this document:** agent behaviour, tool surface, state model, harness, and a step-by-step build plan. **No production code is written yet by design.**

| Decision | Choice |
|---|---|

| House style | Configurable; map to Coditas templates, else define our own |

| Research | Separate capability with graceful degradation |

| Decision | Choice |
|---|---|
| Agent topology | Orchestrator + 3 agents; **architect for three, implement Discovery** |
| Planning / Delivery in v1 | Registered stubs with real permissions and guardrails |

## Part 0 — Read this first

### 0.1 The zero-cost development path

The Claude Agent SDK for Python does not talk to the API directly; it spawns and drives the Claude Code CLI process. That means **it inherits whatever authentication the CLI already has**. If you are logged into Claude Code with your Claude subscription (`claude login`), the SDK runs on that subscription rather than on metered API credits.

Practical consequences for how we build:

- Develop and test with `ClaudeSDKClient` while logged in via the CLI. No `ANTHROPIC_API_KEY` needed.
- **Never hard-code the model or the auth path.** Put both behind a `ModelProvider` seam (§2.18) so you can flip to API keys, or to a cheaper model for eval loops, without touching agent logic.
- Verify before you build on it: run one trivial SDK script on day one and confirm it works with no API key set. If subscription auth is ever restricted for SDK use, the seam above means you change one file.
- **Design for cheap iteration regardless.** Most of this system — the ledger, the coverage engine, the readiness gate, impact analysis — is deterministic Python that needs no model at all. Build and test that with plain `pytest`, no tokens burned. Only the four LLM-dependent surfaces (§2.17) need a live model.

### 0.2 The one thing that determines whether this succeeds

Everything in your requirements document is either (a) a data structure or (b) the question engine. The data structures are a weekend of careful work. **The question engine is the product.**

An agent that stores beautiful versioned requirements but asks fifteen generic questions in a row is worse than useless — the user abandons it at question seven. An agent that asks four sharp questions, infers six things and tells you it inferred them, is a product people keep.

So the design below deliberately spends its complexity budget on:
1. **Deciding what *not* to ask** (§3.2)
2. **The stopping criterion** (§3.6) — the biggest hole in the current spec
3. **Routing "I don't know"** (§3.4)

and keeps the ledger deliberately boring.

## Part 1 — Challenging the intent

This section pushes back on the requirements document. Each item is a real risk, not a nitpick. I've marked what I recommend changing.

### 1.1 Numeric confidence (72%, 85%) is fake precision — **change it**

The spec asks for percentage confidence on assumptions and requirements. LLMs are poorly calibrated at self-reported numeric confidence; 72% and 68% are indistinguishable in practice and will be generated by vibes. Worse, they *look* rigorous, so a user will trust them.

**Recommendation:** replace with a three-value enum plus a mandatory justification.

```
confidence: HIGH | MEDIUM | LOW
confidence_basis: "User stated this explicitly in round 2"   # required, non-empty
```

`HIGH` = user said it. `MEDIUM` = strongly implied by something the user said. `LOW` = agent inferred from domain convention. That mapping is checkable, explainable, and stable. If you later want a number for a dashboard, map the enum to 0.9/0.6/0.3 in the presentation layer — but never let the model emit the number.

### 1.2 "Planning Progress: 68%" has no denominator — **replace it**

Progress against what? You don't know the full question set in advance, so any percentage is invented.

**Recommendation:** a **Coverage Model**. Define a fixed set of named coverage areas up front; progress becomes a real, defensible ratio.

```
COVERAGE AREAS (v1, ~12)
  problem            What problem, for whom, why now
  users              Primary/secondary users, their context
  jobs               What users are trying to accomplish
  scope_in           What v1 includes
  scope_out          What v1 explicitly excludes
  success            How we know it worked (metrics)
  constraints        Budget, deadline, team, compliance
  existing_system    What exists today, integrations
  platform           Web/mobile/desktop, browser support
  data               What data is stored, sensitivity, retention
  nfr                Performance, scale, availability, security
  rollout            Who gets it first, migration, support

Each area has state:
  UNTOUCHED → PARTIAL → SUFFICIENT → CONFIRMED
```

Progress = `(critical areas at SUFFICIENT or better) / (critical areas for this profile)`. Report it against the critical set, not all 12, or the number drifts as non-critical areas fill in. The agent can explain it: *"Critical coverage is 5/7. `success` is PARTIAL — I have a goal but no metric — and `constraints` is UNTOUCHED."*

Critically, **coverage gaps are what generate questions** (§3.2). This isn't just reporting, it's the engine.

### 1.3 There is no stopping criterion — **this is the biggest gap**

The spec says clarification continues "until the agent has enough information to confidently begin research and planning." That phrase is doing enormous unearned work. Without a formal gate, an LLM will either stop too early (it's agreeable) or loop forever.

**Recommendation:** a deterministic **Readiness Gate**, computed in Python, never by the model. See §3.6. The model's job is to *fill* the gate's inputs; the gate itself is arithmetic.

### 1.4 No question budget — the user will abandon — **add one**

Nothing in the spec limits how much you ask. Real users tolerate roughly 3–5 questions per round and 3–4 rounds before they disengage.

**Recommendation:**
- Hard cap: **max 5 questions per round**, target 3.
- Soft cap: after **round 4**, the agent must either pass the readiness gate or explicitly tell the user *"I can proceed on assumptions — here are the six I'd make. Want me to?"*
- Every round must show progress: *"That moved critical coverage from 3/7 to 5/7."* Users tolerate questions far better when they can see the meter move.
- **Track a fatigue signal**: short answers, "whatever", "you decide", "idk" three times running → switch to assumption-heavy mode automatically and say so.

### 1.5 The default is backwards — **flip it to propose-and-confirm**

The spec frames the agent as asking open questions. Open questions ("Who is the target user?") get vague answers from users who haven't thought it through — which is exactly the user you've designed for.

**Recommendation:** the agent's default move is **propose, then confirm**:

> ❌ "Who is your primary target user?"
> ✅ "From 'internal tool for tracking vendor invoices', I'm reading the primary user as an **accounts-payable clerk processing 50–200 invoices a week**, with a finance manager as a secondary approver-only user. Is that right, or is there someone else I'm missing?"

The second version is answerable by someone who doesn't know the answer, because it gives them something to react to. Reaction is cognitively cheaper than generation. This single change probably does more for output quality than the entire versioning subsystem.

Rule to encode in the system prompt: **never ask an open question when you can make a defensible proposal and ask for confirmation.** Open questions are reserved for things where a wrong proposal would anchor the user badly (e.g. "what problem are you actually solving" — anchoring there is dangerous).

### 1.6 "I don't know" is at least five different things — **classify before routing**

The spec treats "I don't know" as one signal with a menu of responses. But these are different situations needing different handling:

| Kind | Signal | Correct route |
|---|---|---|
| **Don't understand** | "What do you mean by that?" | Rephrase in plain language. Do **not** research. |
| **No opinion** | "Whatever you think" | Agent proposes a default → ASSUMPTION, needs confirmation |
| **Depends on something else** | "Depends on the budget" | Identify the dependency, ask *that* question first |
| **Not my call** | "That's the CTO's decision" | → DECISION with an owner ≠ user, DECIDE_LATER |
| **Genuinely unexplored** | "I honestly haven't thought about it" | → **Guidance Mode** (§3.5) |
| **Factually unknown to everyone** | "Which DB scales better here?" | → RESEARCH_REQUIRED, agent owns it |
| **Needs external input** *(added §6.2)* | "That's the client's call" | → open item owned externally; never assume silently |

**Recommendation:** the first thing Guidance Mode does is classify *which* don't-know this is. Only the last two justify the expensive paths. Routing "what do you mean?" into a research subagent is a waste of tokens and a bad user experience.

### 1.7 Guidance Mode as "a tool" is a category error — **make it a subagent**

The spec says "Guidance Mode should be implemented as a dedicated tool." Tools return data in response to arguments. Guidance is a *conversation with a different posture* — it needs to explore, possibly research, compare options, and land on a recommendation.

**Recommendation:** implement Guidance Mode as a **subagent** with its own system prompt and its own tools (web search, ledger read). It returns a structured `GuidanceBrief`:

```json
{
  "dont_know_kind": "genuinely_unexplored",
  "restated_plainly": "...",
  "why_it_matters": "...",
  "what_it_affects": ["REQ-003", "scope_in", "timeline"],
  "options": [
    {"name": "...", "description": "...", "pros": [], "cons": [], "best_when": "..."}
  ],
  "recommendation": {"option": "...", "because": "...", "confidence": "MEDIUM"},
  "what_would_settle_it": "...",
  "safe_default_if_deferred": "...",
  "researched": true,
  "sources": []
}
```

The **main agent renders that brief conversationally** — it does not dump JSON at the user. Keeping it structured means it can also be written to the ledger and replayed later ("why did we pick Postgres?").

### 1.8 Git alone is not enough versioning — **need entity-level history too**

You chose JSON-in-git, which is right. But git history is only accessible by shelling out and parsing `git log`, which the agent will do badly. The agent needs to reason about *"what did REQ-003 look like before, and why did it change?"* without leaving its tool sandbox.

**Recommendation: two layers, one source of truth.**

1. **`events.ndjson` — append-only, the actual source of truth.** Every mutation is an event. Nothing is ever edited or deleted.
2. **Entity JSON files — materialized views**, rebuilt from the event log. These are what git diffs show and what humans read.

This is event sourcing, and it buys you the entire §8 of your spec almost for free: version history, change reason, changed-by, timestamps, and full replay. You can rebuild the whole ledger from events at any time, which also means a corrupted write is recoverable.

```
event: {
  "event_id": "EVT-000142",
  "ts": "2026-09-21T14:32:10+05:30",
  "type": "requirement.revised",
  "entity_id": "REQ-003",
  "actor_id": "...", "actor_role": "agent" | "user",
  "txn_id": "TXN-0041", "workflow_state": "DISCOVERY",
  "source": "clarification_round_3",
  "reason": "User confirmed invites are team-scoped, not project-scoped",
  "before": {...}, "after": {...},
  "session_id": "..."
}
```

### 1.9 Impact analysis will be guesswork unless you build the graph at write time — **make links mandatory**

The spec draws `Requirement Changed → Impact Analysis → Affected Requirements → ...`. If those links don't exist as data, the agent will re-derive them with an LLM call every time, inconsistently.

**Recommendation:** every write tool **requires** its provenance links. A requirement cannot be created without declaring what it derives from.

```
REQ-003:
  derived_from_answers: ["ANS-011"]
  depends_on_assumptions: ["ASM-002"]
  depends_on_decisions:  ["DEC-001"]
  covers_areas:          ["scope_in", "users"]
```

Then impact analysis is a **graph traversal in Python** — deterministic, instant, complete. One name, one place: `analyze_impact()` is an *engine* function (S4.2); agents reach it as `read_planning_state(scope="impact")`, and the Planning Agent's `analyze_plan_impact` in v2 is a different, plan-level operation. The LLM is only used afterwards to *narrate* what the traversal found and judge severity. This is the single highest-leverage "make it code, not prompt" move in the system.

### 1.10 User self-contradiction is unhandled — **add conflict detection**

Round 1: "internal tool, ~20 users." Round 4: "we'll launch it publicly." The spec has no path for this; the agent will most likely just append the new statement and leave the ledger internally inconsistent.

**Recommendation:** after every answer batch, run a **conflict check**: does the new answer contradict any `CONFIRMED` requirement or assumption? If yes, surface it explicitly and make the user choose:

> "This changes something we'd settled. REQ-002 says *internal tool, ~20 users* (you confirmed this on Sep 21). Public launch contradicts that. Should I supersede REQ-002, or are these two different phases?"

Superseding creates a new version with `change_reason` and marks the old one `SUPERSEDED` — which is exactly the mechanism §8 of your spec asks for, now with a real trigger.

### 1.11 The ledger will outgrow the context window — **build a digest from day one**

By round 5 on a real project you'll have 20 requirements, 10 assumptions, 8 decisions, a Q&A log and research findings. Dumping that into context every turn is expensive and degrades attention.

**Recommendation:** a **Ledger Digest** — a generated, compact (~1.5–2k token) projection that the agent reads at the start of every turn. It contains counts, coverage states, all blocking items, all unconfirmed high-impact assumptions, and *titles only* for everything else. Detail is fetched on demand via `query_ledger`. This is not an optimization to add later; the agent's prompt is written against the digest shape, so it has to exist first.

### 1.12 The agent has no clock — **inject the date**

Your spec is heavily date-driven (identified dates, expected decision dates, due dates). The model does not reliably know today's date and will confabulate it.

**Recommendation:** inject `current_datetime` into the system prompt on every turn, and have all date arithmetic (is this overdue? what's the expected decision date?) done in Python tools, never by the model.

### 1.13 Who picks the "expected decision date"? — **make it a rule, not a guess**

The spec requires an expected decision date on every deferred decision but doesn't say where it comes from. An LLM asked to pick one will produce an arbitrary date.

**Recommendation:** derive it. `expected_decision_date = start_of_earliest_phase_this_blocks − buffer`. In v1 (no timeline yet) use a simpler tier rule and state it openly:

```
blocking + affects architecture  → +3 days
blocking + affects scope         → +5 days
non-blocking                     → +14 days, or null with "before build starts"
```

Always show the user the rule and let them override. A date the user didn't set and can't explain is noise.

### 1.14 No evaluation loop — **you can't improve what you don't measure**

Nothing in the spec says how you'd know a prompt change made the agent better. Without this you'll tune by vibes and regress silently.

**Recommendation:** build a small eval harness in step 12. Ten seed requirements (vague → detailed, B2B → consumer, greenfield → legacy), scripted user personas including a deliberately unhelpful one who answers "I don't know" to everything, and a rubric scoring: questions asked to reach the gate, coverage achieved, silent assumptions (should be zero), blocking unknowns missed, and ledger schema violations.

### 1.15 Smaller things worth fixing

- **Deterministic IDs.** `REQ-018` must come from a counter in `project.json` inside a write lock, never from the model. Model-generated IDs collide and drift.
- **Status transitions must be validated.** `CONFIRMED → UNKNOWN` should be rejected by the tool layer. Define the legal transition matrix as data.
- **Idempotency.** A retried tool call must not create a duplicate entity. Use a client-supplied `idem_key` per logical write.
- **Eleven statuses is too many for v1.** Statuses are per-entity, not global — a Decision's lifecycle is not a Requirement's. The v1 set (§2.7) drops five of the spec's eleven, keeping nine across all entities: `ASSUMED`, `UNKNOWN`, `BLOCKED`, `OPEN_DECISION` and `RESEARCH_REQUIRED` are **properties, not statuses** — they become the `blocking`/`route` fields on Unknown and the `confidence` field on Requirement. `RESOLVED` survives only on Unknown, where it does not overlap `CONFIRMED`.
- **"Planning Progress" and "Open Items" should be one command**, not two concepts. One `/status` surface.

## Part 2 — Architecture and execution model

### 2.1 Design stance: architect for three, implement one

v1 scope stays **Clarification + Ledger**. But the Orchestrator, the agent registry, tool permissions, workflow guardrails and the error/recovery model are all built **now**.

```
v1  Orchestrator          IMPLEMENTED
    Discovery Agent       IMPLEMENTED
    Planning Agent        REGISTERED STUB → NOT_IMPLEMENTED
    Delivery Agent        REGISTERED STUB → NOT_IMPLEMENTED
```

The stubs are not placeholders — they are **registered agents with real declared tool permissions and real guardrails**. `create_linear_issue` exists in the registry from day one, owned by Delivery, and is rejected when `plan.status != APPROVED`. That rule is tested in v1 even though no plan can yet reach APPROVED.

Why this matters: the expensive refactor is never "add a feature," it is "add a boundary." Boundaries retrofitted after the fact leak. Adding Planning in v2 should mean replacing a stub's body, not re-architecting dispatch, permissions and state.

### 2.2 There are two loops, and the spec conflates them

This is the most important correction in this section.

**The inner loop is owned by the SDK.** Model emits `tool_use` → runtime executes → results return to context → model reasons again → `end_turn`. It is driven by the API's `stop_reason`, not by parsing text. We do not reimplement it, and attempting to would fight the harness. What we control is which tools exist, what they return, and the hooks around them.

**The outer loop is ours, and it is where every requirement in your spec actually lands.** It is driven by **workflow state and the readiness gate**, not by any model signal at all.

```
                 ┌──────────────── OUTER LOOP (ours, deterministic) ─────────────────┐
                 │                                                                   │
  User request → │ load ledger → determine workflow state → validate preconditions →  │
                 │ select agent → invoke ──┐                            ┌── result →  │
                 │                         │                            │  validate → │
                 │                         ▼                            │  commit →   │
                 │        ┌─── INNER LOOP (SDK, stop_reason) ───┐       │  recover?   │
                 │        │ reason → tool_use → execute →       │       │  escalate?  │
                 │        │ results to context → reason →       │───────┘  continue?  │
                 │        │ end_turn                            │                     │
                 │        └─────────────────────────────────────┘                     │
                 │                                                                   │
                 └───► COMPLETE only when the readiness gate passes ──────────────────┘
```

**Task completion is never a model decision.** The inner loop ending with `end_turn` means *the agent finished its turn* — nothing more. Whether the *task* is complete is answered by `check_readiness()` in Python (§3.6). An agent that says "I'm done" while three blocking unknowns are open simply gets another turn with those unknowns in its digest.

Iteration caps exist at both levels purely as runaway guards: inner turn cap per invocation, outer turn cap per session. Hitting either is logged as an anomaly, never treated as normal completion.

### 2.3 The layer cake

```
┌───────────────────────────────────────────────────────────────┐
│ L7  CLI            typer + rich. Questions, status, briefs.    │
├───────────────────────────────────────────────────────────────┤
│ L6  Orchestrator   Workflow state, precondition validation,    │
│                    agent dispatch, result review, escalation.  │
│                    Owns the OUTER loop. Holds no domain tools. │
├───────────────────────────────────────────────────────────────┤
│ L5  Agents         Discovery (impl) · Planning (stub) ·        │
│                    Delivery (stub). Each: own prompt, own      │
│                    tool grant, own local recovery.             │
├───────────────────────────────────────────────────────────────┤
│ L4  Harness        Agent SDK client, in-process MCP server,    │
│                    hooks, subagents (Guidance, Research).      │
├───────────────────────────────────────────────────────────────┤
│ L3  Tool layer     Role-scoped registry. Permission gate,      │
│                    schema validation, structured results.      │
├───────────────────────────────────────────────────────────────┤
│ L2  Engines        Pure Python, no LLM: coverage, readiness,   │
│                    impact, open items, dates, conflicts.       │
├───────────────────────────────────────────────────────────────┤
│ L1  Ledger         Event log (truth) + materialized entities   │
│                    + digest + audit log + git.                 │
└───────────────────────────────────────────────────────────────┘
```

**Load-bearing rule, unchanged and now enforced in two places:** the model may only change state through L3, and L3 refuses anything L2/L1 schemas reject. Added to that: **L3 refuses anything the calling agent is not granted**, checked before schema (§2.13).

### 2.4 The Orchestrator and the three agents

Each agent declares its identity, its tool grant, and — explicitly — its prohibitions. Prohibitions are enforced by the permission layer, not by prompt text.

**Orchestrator** — coordinates, never plans
- Determines workflow state and which agent owns the current phase
- Runs mandatory precondition validators **itself**, in Python, before dispatch (§2.10)
- Passes scoped context to subagents — never the whole ledger
- Receives structured results; decides continue / recover / escalate / complete
- **Must not** hold domain tools, write requirements, or generate content

**Discovery Agent** *(v1, implemented)* — understand and gather
- Clarification Q&A, unknown detection and classification, "I don't know" routing, "decide later", guidance, research, requirement/assumption/decision management
- **Must not** create a product plan, generate stories, or touch Linear

**Planning Agent** *(v2, stub)* — validated discovery → plan
- Scope, features, flows, technical considerations, dependencies, risks, milestones, timeline, plan versioning, impact analysis, plan review
- **Must not** create Linear issues, invent requirements, or promote an assumption to CONFIRMED without an explicit user confirmation event

**Delivery Agent** *(v3, stub)* — approved plan → implementation work
- Feature/bug/task breakdown, story generation, acceptance criteria, dependencies, priorities, Linear integration
- **Must not** modify approved requirements, or generate work from a plan whose status is not APPROVED

The "must not" lists are not documentation. Each maps to a permission rule (§2.10) and a guardrail test (§2.13 layer 1, Step 12 eval cases 2, 6, 7, 12).

### 2.5 Workflow state machine

Two levels: a **global workflow state** owned by the Orchestrator, and **Discovery's internal modes** owned by the Discovery Agent.

```
GLOBAL (Orchestrator)

  DISCOVERY ──validate_discovery_state()──► DISCOVERY_VALIDATED
                        │ fail                        │
                        └──► back to DISCOVERY        ▼
                                                  PLANNING  (v2 stub)
                                                      │
                                                      ▼
                                                 PLAN_REVIEW
                                                      │ explicit user approval event
                                                      ▼
                                                 PLAN_APPROVED
                                                      │
                                                      ▼
                                                  DELIVERY  (v3 stub)
                                                      │
                                                      ▼
                                                   COMPLETE

  CHANGE_REQUESTED ── reachable from every state above ──► impact analysis
                                                        ──► rewind to the
                                                            earliest affected state
```

```
DISCOVERY-INTERNAL (Discovery Agent)

  INTAKE → CLARIFY ⇄ GUIDANCE → RESEARCH → REVIEW → READY
                └──────── CHANGE reachable from all ────────┘
```

v1 runs the global machine from `DISCOVERY` to `DISCOVERY_VALIDATED` and stops there — attempting to advance returns a structured `NOT_IMPLEMENTED` from the Planning stub, which the Orchestrator renders as *"Planning is v2. Discovery is validated and the ledger is ready for it."*

The transition table is data, in `workflow/transitions.yaml`, so guardrails are inspectable rather than buried in conditionals.

### 2.7 Ledger entities (v1)

Seven entity types (`Question`/`Answer` share a record with two ID series, `Q-nnn` and `ANS-nnn`). Every one carries `id`, `version`, `status`, `created_at`, `updated_at`, `created_by`, `updated_by`, `history[]`.

**Requirement** — `REQ-nnn`
```
statement, type (functional|non_functional|constraint),
status (PROPOSED|CONFIRMED|REJECTED|SUPERSEDED),
confidence, confidence_basis,
covers_areas[], derived_from_answers[],
depends_on_assumptions[], depends_on_decisions[],
priority (must|should|could|wont_v1),
needs_user_confirmation: bool, custom_fields{}
```

**Assumption** — `ASM-nnn`
```
statement, reason, impact (HIGH|MEDIUM|LOW),
confidence, confidence_basis,
status (PROPOSED|CONFIRMED|REJECTED|SUPERSEDED),
affects_requirements[], affects_areas[],
user_confirmation_required: bool, confirmed_at, confirmed_by,
provisional: bool          # true when pending external/client input (§6.2)
```

**Decision** — `DEC-nnn`
```
question, status (OPEN|DECIDE_LATER|DECIDED|SUPERSEDED),
blocking: bool, owner, owner_type (user|external|agent),
identified_at, expected_decision_date, decided_at,
defer_reason, options[], chosen_option, rationale, prerequisites[],
current_assumption, related_requirements[], related_research[]
```

**Unknown** — `UNK-nnn`
```
question, area, why_it_matters,
blocking: bool,                  # does this stop planning?  ← gate reads this
route (GUIDANCE|RESEARCH|USER_DECISION|ASSUMPTION|OPTIONAL|FUTURE),
                                 # how it gets resolved      ← router reads this
owner_type, status (OPEN|RESOLVED|CONVERTED), converted_to
```

**Question / Answer** — `Q-nnn` / `ANS-nnn`
```
text, why_asked, target_areas[], round,
suggested_options[], recommended_default,
answer_kind (answered|dont_know|decide_later|not_relevant),
dont_know_kind, answer_text, answered_at
```

**ResearchFinding** — `RES-nnn`
```
question, method, summary, options_found[], sources[],
confidence, confidence_basis, researched_at,
stale_after_days (default 90, §6.5), feeds_decision
```

**Risk** — `RSK-nnn` *(thin in v1)*
```
statement, likelihood, impact, area, mitigation,
status (OPEN|MITIGATED|ACCEPTED|CLOSED)
```

**Why `blocking` and `route` are separate fields.** An earlier draft had one
`classification` enum containing both `BLOCKING` and `RESEARCH_REQUIRED`. That
made "blocking *and* needs research" — a common, important case — literally
unrepresentable, while §6.5's gate rule depended on it. Severity and resolution
path are orthogonal: split them. The gate reads `blocking`; the router reads
`route`.

**Risk is declared but not written in v1.** `RSK-nnn` has no Discovery writer;
the Planning Agent owns it in v2. It is defined here so the schema does not
change when Planning lands.

**Coverage is computed, not declared.** My earlier draft had an `update_coverage` tool. That was wrong — it let the model self-report its own progress, which is exactly the number you cannot trust. Area state is now derived by the coverage engine from which entities cover which areas and at what confidence. The model changes coverage only by recording real entities.

### 2.8 Tool distribution by agent

Role-scoped, not one global toolkit. CRUD-style writers consolidate into parameterized `manage_*` tools with a controlled `operation` enum.

**Orchestrator — 5**
| Tool | Purpose |
|---|---|
| `read_workflow_state` | Current global state, gate result, active agent. |
| `invoke_discovery` | Dispatch to Discovery with scoped context. |
| `invoke_planning` | Dispatch to Planning. v1: returns NOT_IMPLEMENTED. |
| `invoke_delivery` | Dispatch to Delivery. v1: returns NOT_IMPLEMENTED. |
| `review_subagent_result` | Validate a structured agent result; decide next action. |

**Discovery — 7** *(v1)*
| Tool | Purpose |
|---|---|
| `read_planning_state(scope, …)` | All reads and deterministic analyses: `digest \| entity \| history \| coverage \| open_items \| readiness \| impact`. |
| `manage_requirement(operation, …)` | `create \| revise \| confirm \| reject \| supersede`. |
| `manage_assumption(operation, …)` | `create \| confirm \| reject \| modify \| supersede`. |
| `manage_decision(operation, …)` | `open \| defer \| decide \| supersede`. |
| `manage_unknown(operation, …)` | `record \| classify \| resolve \| convert`. |
| `ask_user(questions[])` | ≤5 questions with options, defaults, four affordances. |
| `request_guidance(question_id)` | Invoke the Guidance subagent. |

**Why 7 and not 5.** Merging the four `manage_*` tools into one `manage_entity` would hit the target number while moving the same selection problem inside the tool — the model would pick `entity_type` as a parameter, against a description covering four schemas. These four have different schemas, different validation rules and different failure modes, so they stay separate. Folding all reads into one `read_planning_state` is the opposite case: same permission, same failure modes, no writes, so consolidation is a real simplification. **Flagged for eval:** if Step 12 shows confusion between `manage_unknown` and `manage_decision`, merge those two — they are the closest pair.

**Guidance and Research subagents — 2 each** *(v1)*
`read_planning_state` · `manage_research` — plus web search for Research.
These are registered agents with their own grants, not prompt personas. This is
what makes `RES-nnn` writable: no top-level agent can write a research finding,
which is correct — findings are produced by the subagent that did the work, and
§2.3's rule ("state changes only through L3") holds without an exception.

**Planning — 5** *(v2, declared and stubbed now)*
`read_planning_state` · `manage_plan` · `manage_milestone` · `manage_timeline` · `analyze_plan_impact`

**Delivery — 5** *(v3, declared and stubbed now)*
`read_approved_plan` · `generate_story` · `validate_story` · `manage_linear_issue` · `read_planning_state`

### 2.9 The tool description contract

Every tool is defined by a `ToolSpec` with thirteen mandatory fields — your eleven required elements, plus `name` and `purpose` as separate fields. Because it is a dataclass and not prose, **a test can assert that every registered tool has all eleven populated** — ambiguity becomes a CI failure rather than a debugging session.

```python
ToolSpec(
    name, purpose,
    inputs,              # field → type, constraint
    required, optional,
    formats,             # regex/enum/range per field
    returns,             # success shape
    examples,            # ≥2 realistic calls
    edge_cases,
    limitations,
    use_when,            # ≥2 explicit conditions
    do_not_use_when,     # ≥2 explicit conditions
    related_tools,       # name → how this differs
)
```

Worked example, showing the boundary that matters:

```
manage_linear_issue
  purpose:   Create or update an implementation issue in Linear from an
             approved Delivery story.
  use_when:  · workflow_state == PLAN_APPROVED
             · the story passed validate_story
             · the story traces to a requirement with status CONFIRMED
  do_not_use_when:
             · the plan is draft or in review        → returns BUSINESS error
             · any blocking requirement is unresolved → returns BUSINESS error
             · the user is still in Discovery         → returns PERMISSION error
             · the user only asked a clarifying question
  related:   generate_story — produces the story; does NOT push it anywhere.
             validate_story — checks a story; never creates an issue.
```

### 2.10 Permission enforcement, and mandatory validation

**Permissions are programmatic.** The tool dispatcher takes the calling agent's identity from the invocation context — never from the model's claim — and checks the registry grant before anything else happens. A Discovery Agent emitting `manage_linear_issue` gets a `PERMISSION` result; the tool body never runs. The grant table is data (`agents/registry.py`), and a test enumerates every (agent, tool) pair against it.

**Mandatory steps are executed by the Orchestrator, not requested from the model.** Your §8 proposes forced `tool_choice`. That works at the raw Messages API level, but the Agent SDK does not reliably expose per-turn tool forcing, and a design that depends on it is fragile. The stronger construction:

```python
# orchestrator/dispatch.py
def advance_to_planning(ledger):
    result = preconditions.validate_discovery_state(ledger)   # plain Python
    if not result.ok:
        return route_back_to_discovery(result.blockers)
    return invoke(PlanningAgent, scoped_context(ledger))
```

The model cannot skip the validation because **the model is never asked to perform it**. Same guarantee, no dependency on runtime internals, and it is unit-testable without a model. Where the model *should* choose freely, `tool_choice` stays auto; that is the correct use of the setting.

### 2.11 The execution loop

```
OUTER (Orchestrator, per turn)

 1  load ledger → digest, workflow state, ledger_version
 2  evaluate readiness gate                          ── deterministic
 3  if gate passed and state == terminal → COMPLETE
 4  validate preconditions for the next state         ── deterministic
 5  select agent from workflow state                  ── table lookup
 6  open transaction (txn_id, checkpoint = ledger_version)
 7  invoke agent  ───────────► INNER LOOP (SDK-managed)
 8  receive structured AgentResult
 9  classify: OK · PARTIAL · RECOVERABLE · NON_RECOVERABLE ·
              HUMAN_INPUT_REQUIRED · WORKFLOW_TRANSITION · NOT_IMPLEMENTED
10  OK/PARTIAL          → validate, commit txn, regenerate digest, git commit
    RECOVERABLE         → local recovery already tried; retry budget at this level
    HUMAN_INPUT_REQUIRED→ surface question/approval, suspend (not an error)
    WORKFLOW_TRANSITION → update state, loop
    NON_RECOVERABLE     → roll back txn, preserve partials, escalate
11  loop
```

Outer iterations are capped per session as a runaway guard only; reaching the cap writes an `anomaly.loop_cap_reached` event and escalates. It never counts as completion.

### 2.12 Structured results and the error taxonomy

Every tool returns the same envelope. `recommended_action` is an enum and is **always populated** — the field the caller acts on.

```json
{
  "success": false,
  "degraded": false,
  "result_count": 0,
  "data": null,
  "error": {
    "category": "TRANSIENT",
    "code": "LEDGER_WRITE_TIMEOUT",
    "is_retryable": true,
    "retry_after_ms": 400,
    "description": "Ledger write timed out. The request was valid but storage did not complete.",
    "recommended_action": "RETRY_SAME",
    "context": {"ledger_version": 12, "txn_id": "TXN-0041"}
  }
}
```

| Category | Examples | `is_retryable` | `recommended_action` |
|---|---|---|---|
| `TRANSIENT` | timeout, rate limit, temporary unavailability | **true** | `RETRY_SAME` (with backoff) |
| `VALIDATION` | missing field, bad enum, invalid id | false | `CORRECT_AND_RETRY` |
| `BUSINESS` | plan not approved, blocking requirement open | false | `CHANGE_WORKFLOW` |
| `PERMISSION` | agent not granted this tool | false | `ABORT_AND_ROUTE` |
| `NOT_IMPLEMENTED` | Planning/Delivery stub invoked in v1 | false | `INFORM_USER` |

**On `is_retryable`.** The flag answers exactly one question: *will sending this identical request again likely succeed?* Your spec is right that `false` does not mean "abandon the task" — but a boolean invites exactly that misreading, by model and by developer. Hence `recommended_action`: it is directive, it is enumerable, and it can be asserted in tests. Treat `is_retryable` as advisory and `recommended_action` as the contract.

**Empty success is not failure.** A research query that runs and finds nothing returns `success: true, result_count: 0` and the agent continues. A research service timeout returns `success: false, TRANSIENT`. The two must never be conflated in either direction — an eval case covers each (Step 12, cases 8 and 5).

**`degraded: true`** is the third state your spec implies but doesn't name: the operation succeeded with reduced capability — research ran without web access, for instance (§6.5). Success, with an honest caveat attached, not an error.

### 2.13 Validation layers — and the order matters

Five layers, but **permission runs first**, which is a change from the order in your spec.

| # | Layer | Where | Rejects |
|---|---|---|---|
| **1** | **Permission** | dispatcher, pre-body | agent not granted this tool |
| 2 | Schema | PreToolUse hook (Pydantic) | types, enums, formats, required fields |
| 3 | Workflow | orchestrator + tool guard | action illegal in current state |
| 4 | Semantic | tool body | CONFIRMED requirement whose target user is UNKNOWN |
| 5 | Ledger consistency | store, pre-append | version mismatch, dangling refs, illegal transition |

Permission first for two reasons: it is the cheapest check, and a permission failure should not leak schema details about a tool the caller may not use. Workflow before semantic because workflow is a table lookup while semantic validation may need to load related entities.

Guardrail examples, each a rule in `workflow/transitions.yaml` and a test:

```
plan.status != APPROVED           → manage_linear_issue          REJECT (BUSINESS)
any blocking Unknown still OPEN  → advance to PLANNING          REJECT, route to Discovery
critical assumption unconfirmed   → plan approval                BLOCK
caller == DiscoveryAgent          → manage_linear_issue          REJECT (PERMISSION)
caller == DeliveryAgent           → manage_requirement           REJECT (PERMISSION)
```

### 2.14 Transactions, checkpoints and recovery

Event sourcing makes this cheap: **validation happens before append, and the append is the commit.** A rejected write leaves nothing to roll back.

Multi-event operations need a marker so a crash mid-sequence cannot leave a half-state:

```
txn.begin     {txn_id, checkpoint_version}
  … events, each carrying txn_id …
txn.commit    {txn_id}          ← materializer ignores any txn without this
```

Sequence for state-changing work:
1. Read `ledger_version` → checkpoint
2. `txn.begin`
3. Execute, validating each step
4. On any failure → no `txn.commit`; write `txn.abort` with the reason and partial results
5. On success → `txn.commit`, rematerialize, regenerate digest, git commit

**Retry is bounded per operation, not globally.** Budget of 3 for `TRANSIENT` with exponential backoff; exhaustion produces a `PARTIAL_FAILURE` result carrying attempts, successes, failures, partial results and a recommended next action — never a bare failure.

**Local recovery first.** A Discovery research timeout is retried inside Discovery. The Orchestrator is only involved when the agent cannot resolve it locally, and the propagated result says what was attempted:

```json
{ "status": "PARTIAL_FAILURE", "attempted": 5, "successful": 3, "failed": 2,
  "error_category": "TRANSIENT", "partial_results": [...],
  "next_action": "ESCALATE_TO_ORCHESTRATOR" }
```

### 2.15 Human escalation

Escalation is a first-class outcome, not a failure path. Triggered by: a critical requirement that cannot be determined, conflicting user decisions, a business-rule conflict, a permission conflict, repeated tool failure past budget, plan approval, or a high-impact assumption awaiting confirmation.

Every escalation states, in this order: **what happened · what is missing · what was attempted · what the options are · what decision is needed.** An escalation that does not end in a concrete question is a bug — the user should never have to ask "so what do you want from me?"

### 2.16 Audit trail

Two logs, deliberately separate:

- **`events.ndjson`** — state changes only. Replayable, the source of truth. Keeping it semantic is what makes `rebuild_all()` fast and readable.
- **`audit.ndjson`** — every tool invocation including reads, rejections and retries. Observability, never replayed.

Audit record:
```
agent · tool · operation · ts · workflow_state · inputs_ref (hash+pointer,
never raw payload — §2.19.1) · reason ·
result(success|category|code) · validation_layer_failed · retry_attempt ·
ledger_version_before · ledger_version_after · txn_id
```

```
DiscoveryAgent · request_guidance · DISCOVERY
  reason: USER_SELECTED_I_DONT_KNOW · result: SUCCESS · ledger 12 → 13
```

This makes `ppa why <id>` (S13.4) able to answer not just *what changed* but *which agent changed it, under which tool, in which state, and why*.

### 2.17 Where the LLM is actually needed

Only four surfaces:

1. **Interpretation** — seed requirement → proposed understanding; free-text answers → structured entities.
2. **Question generation and selection** — candidates, information-gain judgment.
3. **Guidance** — explaining a decision, generating and comparing options.
4. **Narration** — turning deterministic engine output into readable prose.

Everything else is Python: progress, readiness, impact traversal, dates, IDs, status validity, open items, permissions, workflow transitions, retry decisions, conflict *candidate* detection. Stable, fast, free to test.

### 2.18 Harness specifics (Claude Agent SDK)

- **`ClaudeSDKClient`** per agent invocation, with the agent's own system prompt and `allowed_tools` from its registry grant. The grant is enforced again at dispatch — `allowed_tools` is a hint to the model, not a security boundary.
- **In-process MCP server** (`create_sdk_mcp_server` + `@tool`) so tools share ledger objects directly.
- **Subagents** for Guidance and Research with isolated context, so a research detour does not pollute clarification context.
- **Hooks:** `PreToolUse` → permission, schema, workflow. `PostToolUse` → event append, materialize, digest, audit record.
- **`ModelProvider` seam** — model and auth in one place; subscription-via-CLI now, API key or a cheaper eval model by config.
- **Context:** system prompt + digest + last N turns. Never the raw ledger.

### 2.19 Security and permissions

The operating principle: **an agent can do only what its role, the current workflow state, and its explicit grants allow.** Four of the six controls below already exist elsewhere in this document; two are new and one closes a gap the ledger design created.

| Control | Where it lives | Status |
|---|---|---|
| Least privilege | §2.8 role-scoped grants | designed |
| Programmatic enforcement | §2.10 dispatcher + S5.2 | designed |
| Workflow permissions | §2.13 guardrails + eval case 12 | designed |
| Audit trail | §2.16 `audit.ndjson` | designed |
| **Secrets and ledger data** | **§2.19.1** | **new** |
| **Approval for irreversible actions** | **§2.19.2** | **new** |

#### 2.19.1 Secrets, and what the ledger is actually holding

Two distinct problems, often conflated.

**Credentials the system uses.** API keys and tokens come from environment variables or the OS keychain, resolved at call time by the `ModelProvider` and `ResearchProvider` seams. They are never written to the ledger, never placed in a prompt, never logged. The audit record stores `inputs_ref` — a content hash and entity pointer — rather than raw tool inputs, so a payload that happened to contain a credential does not land in the audit log either.

**Credentials and client data users type in.** This is the realistic exposure and it is created by our own design: `ask_user` answers are free text, they become `ANS-nnn` entities in `events.ndjson`, and S2.7 **auto-commits every turn to git**. An engineer scoping client work, asked "how does this integrate with your existing system," will eventually paste a connection string.

Three mitigations, matching the locked decision — protect obvious secrets automatically, keep client data local by default, let the user control where the ledger goes:

1. **Inbound secret scanning.** Before any answer or free-text field is appended, run pattern detection (common API key shapes, `postgres://`/`mysql://` URIs with credentials, private key headers, `Authorization:` headers, long high-entropy strings). A hit is **redacted to `[REDACTED:credential]` before the event is written** — never after, because the event log is append-only and there is no unwriting. The user is told inline: *"I've redacted what looks like a credential from that answer. If it matters to the requirement, describe it rather than pasting it."* False positives are recoverable (the user rephrases); a written secret is not.

2. **Local by default.** `create_project` configures **no git remote**. The ledger is a local repo unless the user deliberately adds one. A `.gitignore` template excludes any `*.local.*` and a `scratch/` path for things users want kept out entirely.

3. **Stated plainly.** The README and `ppa new` output both say: *the ledger contains your requirements and answers verbatim, including client information; it is a local git repo; add a remote only if that is appropriate for this project.* Most of this risk is solved by the user knowing it exists.

**Explicitly out of scope for v1:** encryption at rest, per-project sensitivity classification, key management. Single-user, local-only, no remote by default is a coherent posture. Revisit when multi-user or a hosted deployment arrives — both change the threat model entirely.

#### 2.19.2 Approval gates for irreversible actions

Permission answers *may this agent do this*. Approval answers *does the user want it done*. Separate questions, separate gates.

An action needs an approval gate when it is **external** (leaves the system), **irreversible** (no clean undo), or **bulk** (one decision creating many artifacts). Creating Linear issues is all three.

**Model: dry-run preview, then explicit batch approval.**

```
Delivery Agent has N validated stories
   │
   ▼
1  DRY RUN      render exactly what would be created —
                titles, descriptions, acceptance criteria, labels,
                assignees, parent/child links. Nothing leaves the system.
   ▼
2  PRESENT      full preview + a diff if any issue already exists
   ▼
3  APPROVE      one explicit approval for the batch, recorded as
                approval.granted {scope_hash, story_ids[], granted_at,
                                  granted_by, expires_at}
   ▼
4  EXECUTE      manage_linear_issue checks the approval covers THIS
                scope_hash. Any change to the story set invalidates it.
   ▼
5  RECORD       per-issue result events; partial failure preserved,
                never silently retried into duplicates
```

`scope_hash` is what makes the gate meaningful rather than ceremonial: it is computed over the exact story set being created. If a story is edited, added or removed after approval, the hash changes, the approval no longer covers it, and re-approval is required. An approval that survives arbitrary changes to what it approved is not an approval.

Batch rather than per-issue is deliberate. Forty individual confirmations produce rubber-stamping, which is worse than one considered decision made against a complete preview.

Approvals expire (default 24h) so a stale approval cannot be replayed into a later session.

**Built in v1 against the stubs.** The gate, the `scope_hash` check, the approval events and the expiry all exist and are tested before Linear is real — same reasoning as the agent stubs in §2.1. Eval case 12 extends: creating an issue with no approval, with an expired approval, or with an approval whose `scope_hash` no longer matches must each return `BUSINESS` and create nothing.

**Also gated:** the `PLAN_REVIEW → PLAN_APPROVED` transition (§2.5) — distinct from §3.6 condition 7, which approves the Discovery *review summary*, a different artifact at a different stage. And `force-ready` (§3.6), a user override of a safety gate, recorded as an event listing everything skipped.

#### 2.19.3 What v1 deliberately does not do

Authentication, authorization beyond agent roles, multi-tenancy, encryption at rest, rate limiting, and network egress control are all out of scope. Single-user, local, no default remote. Each becomes relevant with multi-user support or a hosted deployment, and each should be designed against that threat model rather than guessed at now.

## Part 3 — The intelligence layer

This is the part worth getting right. The rest is plumbing.

### 3.1 Intake: build an understanding before asking anything

The worst version of this product opens with "Tell me about your target users." The best version opens by demonstrating it already understood something.

On receiving the seed requirement, **before any question**, the agent:
1. Writes a 3–6 sentence **Initial Product Understanding** — what it thinks is being built, for whom, why.
2. Drafts 3–8 requirements as `PROPOSED` with `LOW`/`MEDIUM` confidence.
3. Records every inference as an `ASSUMPTION` with `user_confirmation_required: true`.
4. Lets the coverage engine recompute — areas the proposed requirements and assumptions touch move off `UNTOUCHED` as a *consequence* of step 2–3, never by the agent declaring a state (§2.7).
5. Shows all of it and asks *one* thing: **"Where am I wrong?"**

That opening move earns trust and harvests corrections faster than any question would.

### 3.2 The question engine — deciding what *not* to ask

Every round:

**Step A — Find gaps (deterministic).** Coverage areas below `SUFFICIENT`, ranked by criticality.

**Step B — Generate candidates (LLM).** For each gap, produce candidates with mandatory metadata:
```
{ text, target_area, why_it_matters, blocking: bool,
  answerable_by: "user_only" | "research" | "agent_inference",
  proposed_default, options[] }
```

**Step C — Filter (deterministic + LLM judgment).** This is where the value is:
- `answerable_by == "agent_inference"` and confidence ≥ MEDIUM → **do not ask.** Record an ASSUMPTION, flag for confirmation, move on.
- `answerable_by == "research"` → **do not ask.** Record UNKNOWN as `RESEARCH_REQUIRED`, queue it.
- Already answered, or derivable from an existing entity → **drop silently.**
- Not blocking and coverage area not critical → **defer to the backlog**, don't spend a slot.

**Step D — Score and select.**
```
priority = (2.0 if blocking else 1.0)
         × information_gain          # how many areas/decisions it unblocks
         × user_answerability        # can THIS user plausibly answer it?
         ÷ cognitive_cost            # how hard is it to think about
```
Take the top 3 (max 5). Prefer a spread across areas over three questions about the same area — breadth surfaces unknown-unknowns faster.

**Step E — Shape each question.** Every question shipped to the user carries:
- Plain-language text, no jargon
- *Why I'm asking* (one line) — this is what converts a questionnaire into a partner
- 2–4 concrete options where they exist
- A **recommended default** with reasoning
- Four affordances: **Answer · I don't know · Decide later · Not relevant**

### 3.3 The unknown classification rule

One rule decides the route:

> **Can planning continue and stay correct without this?**

```
                                    blocking   route
NO, and only the user knows it      true       GUIDANCE       ask, guide if needed
NO, but it's a factual question     true       RESEARCH       agent owns it
NO, but a safe default exists       false      ASSUMPTION     state it, confirm later
YES, needed before build            false      USER_DECISION  date it, own it
YES, needed later or maybe never    false      OPTIONAL       backlog, raise at review
```

The two fields are independent: a blocking unknown that needs research is
`blocking=true, route=RESEARCH`, which the old single-enum model could not express.

Worked examples, matching your spec's table:

| Question | `blocking` · `route` | Agent action |
|---|---|---|
| What problem are we solving? | `true` · GUIDANCE | Never assume. Guidance Mode if unknown. |
| Who is the target user? | `true` · GUIDANCE | Propose from context, confirm. Guidance if still unclear. |
| Which database? | `false` · RESEARCH | Research, present 2–3 options + recommendation. |
| Which auth model? (shapes scope) | `true` · RESEARCH | Blocking **and** researchable — the case the old enum couldn't hold. |
| Expected traffic? | `false` · ASSUMPTION | Estimate from user count and stated scale; flag it. |
| Deployment provider? | `false` · USER_DECISION | Date it against build start. |
| Pricing model? | `false` · USER_DECISION | Owner = user. Set `blocking=true` only if it shapes scope. |
| Exact UI colour? | `false` · OPTIONAL | Backlog. Never spend a question slot on this. |

### 3.4 Handling "I don't know"

```
User: "I don't know"
   │
   ▼
Classify the don't-know (§1.6)  ── Guidance subagent, first pass
   │
   ├─ don't_understand   → rephrase plainly, re-ask. No research. Cheap.
   ├─ no_opinion         → propose a default → ASSUMPTION (confirm required)
   ├─ depends_on_X       → record dependency, ask about X first, return later
   ├─ not_my_call        → DECISION, owner ≠ user, DECIDE_LATER + date
   ├─ unexplored         → FULL GUIDANCE MODE (§3.5)
   ├─ factually_unknown  → RESEARCH_REQUIRED, agent owns, report back
   └─ needs_external_input → open item, owner_type: external; provisional
                             assumption flagged "pending client confirmation";
                             accumulates into the client questionnaire (§6.2)
```

**Hard rule for the system prompt:** the agent never re-asks the same question in the same form. If a reframed question also returns "I don't know," it must escalate to a different route — never loop.

### 3.5 Guidance Mode

Triggered on `unexplored`, on explicit user request ("help me think about this"), or after two failed reframings.

The subagent runs this sequence:
1. **Restate plainly.** Strip jargon. Confirm it's the right question.
2. **Explain the stakes.** What breaks later if we get this wrong. Concretely, with reference to the actual product, not generically.
3. **Narrow with sub-questions.** For target users: *"When you imagine someone opening this, are they doing their own job, or managing someone else's?"* Easier to answer than the original.
4. **Research if the question is factual.** Web search, ledger context.
5. **Present 2–4 options** with pros, cons, and "best when."
6. **Recommend one**, with reasoning and confidence.
7. **Land it** — user picks, or defers (→ DECIDE_LATER with a safe default recorded as an ASSUMPTION so planning continues).

The brief is written to the ledger as a `RES-nnn` linked to the resulting `DEC-nnn`, so the rationale survives the conversation.

### 3.6 The Readiness Gate

Pure Python. No model. Returns pass/fail **and the precise blocking list** so the agent can explain itself.

```python
READY  ⟺  all of:

  1. every coverage area CRITICAL FOR THIS USER PROFILE is SUFFICIENT
     or CONFIRMED  (the critical set is a per-profile lookup, §6.1 —
     not a fixed list)

  2. zero Unknowns with blocking == True and status == OPEN,
     EXCEPT those with owner_type == external, which convert to a
     provisional assumption and do not block  (§6.2)

     Note this is stated in terms of `blocking`, not of `route`. An
     unresearched item blocks only if it is itself blocking; a
     non-blocking RESEARCH item is an open item, not a gate failure (§6.5).

  3. every Assumption with impact == HIGH has status in {CONFIRMED, REJECTED}
     (a provisional assumption from an external-owned item satisfies this
     only after the user acknowledges it in REVIEW)

  4. every Decision with blocking == True has status == DECIDED
     (DECIDE_LATER is permitted ONLY for blocking == False)

  5. at least one Requirement covers each critical area

  6. zero unresolved conflicts

  7. the user has explicitly approved the REVIEW summary
```

Two escape hatches, because a rigid gate is its own failure mode:

- **`/force-ready`** — user overrides. The agent records an event, lists everything being skipped, and every unresolved item becomes a tracked open item. Some users know what they're doing.
- **Round-4 offer** — if the gate hasn't passed after 4 rounds, the agent proactively says: *"Critical coverage is 5/7. I can close the remaining two with assumptions — here they are. Approve and we proceed, or keep going."*

### 3.7 Conflict detection

After each answer batch:
1. Deterministic candidate detection — entity/area overlap between the new answer and existing `CONFIRMED` entities.
2. LLM adjudicates each candidate: real contradiction, refinement, or unrelated?
3. Real contradictions are surfaced immediately with both versions, dates, and the supersede/branch choice.
4. On supersede → new entity version + impact traversal + report affected items.

### 3.8 The status board (`/status`)

One command, rendered by `render/status_board.py` from engine output only — the model does not compose this.

```
PLANNING STATUS — Invoice Tracker            Session 3 · 2026-09-21 14:32

Coverage  6/7 critical ██████████░░   all areas 8/12   Round 3 · CLARIFY

  critical  ✓ problem ✓ users ✓ jobs ✓ scope_in ✓ success ✓ constraints
            ◐ scope_out (PARTIAL)
  other     ✓ existing_system ✓ platform   ○ data ○ nfr ○ rollout

Ledger
  Requirements   14   (11 confirmed · 3 proposed)
```

### STEP 2 — Ledger store
*Est. 2 days · No LLM*

**S2.1 — Append-only event log** — NDJSON, exclusive file lock, monotonic IDs. *Done when:* 1000 concurrent appends produce 1000 well-formed lines, no interleaving. **Note the single-writer assumption in the README** (§6.6).

- *Do:* pattern detection (API key shapes, credentialed DB URIs, private key headers, `Authorization:` headers, high-entropy strings) on every free-text field; redact to `[REDACTED:credential]`; notify the user inline.

### 6.1 Role-adaptive questioning is now a first-class input (from #1)

"Adapt vocabulary based on the user's role" sounds like a prompt instruction. It isn't — if role only lives in the prompt, the question engine will still generate NFR questions for a PM who can't answer them and burn question slots.

**Role becomes an input to the scoring function.** The `user_answerability` term in §3.2 Step D was a placeholder; it now has a real source.

Add to `project.json`:
```yaml
user_profile:
  role: engineer | product | mixed        # who is at the keyboard
  technical_depth: high | medium | low
  domain_familiarity: high | medium | low # do they know the problem domain?
```

**Coverage criticality stops being a fixed boolean.** In §1.2 criticality was a fixed property of the area. That's now a per-profile lookup, because what must be nailed down before planning differs by who's planning:

| Coverage area | Engineer answers directly | Product answers directly | Neither → route |
|---|---|---|---|
| problem, users, jobs | needs guidance | direct | guidance, always |
| scope_in, scope_out | direct | direct | — |
| success (metrics) | needs guidance | direct | guidance |
| constraints | direct | partial | ask |
| existing_system | direct | needs guidance | ask engineer |
| platform, data, nfr | direct | needs guidance | guidance or research |
| rollout | needs guidance | direct | guidance |

The practical effect: for an engineer profile the agent asks `nfr` and `data` questions plainly and *guides* on `problem` and `success`. For a product profile it inverts. **This is a reordering of question priority, not just a vocabulary swap.**

**Build impact:** new sub-step S1.5; the coverage engine (S4.1) reads criticality from the profile; the Discovery prompt (S7.1) gets a role-conditioned vocabulary section.

### 6.2 The client-work case your answer implies (and the taxonomy missed)

You said Coditas engineers working on **client** projects. That surfaces a don't-know kind my §1.6 table doesn't cover, and it will be the most common one in agency work:

> The engineer at the keyboard doesn't know — **and can't know** — because the answer lives with the client.

This is not `unexplored` (guidance won't help), not `factually_unknown` (research won't help), and not `no_opinion` (assuming is actively dangerous — you'd be inventing the client's requirements).

**New don't-know kind: `needs_external_input`.**

```
needs_external_input → record as open item with owner_type: external
                     → do NOT guide, do NOT research, do NOT assume
                     → agent may record a PROVISIONAL assumption, clearly
                       marked as "pending client confirmation"
                     → accumulate into a generated client questionnaire
```

The payoff: **the agent produces the client question list as a byproduct of planning.** An engineer runs a clarification session, and out falls a clean, prioritised, "here's what we need from you" document — with each question carrying why it matters and what we'll assume in the meantime. For a services business that's plausibly the most commercially valuable thing this agent does, and it costs almost nothing extra to build.

**Schema change:** `owner_type: user | external | agent` on Decision and Unknown (alongside the existing free-text `owner`).

**New command:** `ppa client-questions` → renders all `owner_type: external` open items as a sendable document, grouped by area, with provisional assumptions flagged.

**Readiness gate:** external-owned blocking items do **not** prevent READY — otherwise every client project stalls. They convert to tracked provisional assumptions and appear prominently in the REVIEW summary. This is a deliberate exception to gate condition 2.

**Build impact:** sub-step S8.4; small addition to S10.3.

### 6.3 House style belongs at the edge, never in the core schema (from #3)

The trap here is real and expensive: let client templates into the entity model, and every new client template variation forks your schema. Six months in you have `requirement_v2_acme` and nobody can run impact analysis across projects.

**The rule: the canonical ledger schema is fixed. House style is three things at the boundary.**

1. **Export/render mapping** — canonical entity → template shape, applied on output only.
2. **`custom_fields: dict[str, Any]`** on each entity, validated against the active style config. Org-required fields live here, never as new top-level schema.
3. **Terminology overrides** — if Coditas says "Feature Brief" where we say "Requirement," that's a label map, not a rename in code.

```yaml
# config/house_style.yaml
name: coditas_default
terminology:
  requirement: "Requirement"
  story: "User Story"
requirement:
  required_custom_fields: [module, client_ref]
  template: templates/coditas_requirement.md.j2
story:                                  # v3, defined now so v1 doesn't block it
  template: templates/coditas_story.md.j2
  fields: [id, title, description, acceptance_criteria, estimate, priority]
export:
  format: markdown | json | jira_csv
```

Two things worth acting on now:

- **This matters in v1, not v3.** The requirement template is used from the first session. Don't defer the style layer to story generation.
- **Find the existing templates before inventing ours.** If Coditas has a standard requirements or story format in use on client work, mapping to it now is cheap; retrofitting after fifty projects is not. Worth twenty minutes asking around before S1.6.

**Build impact:** sub-step S1.6; `render/` reads the style config.

### 6.4 "Semi-opinionated" needs to be a number, or the model decides (from #4)

"Never silently decide **important** product requirements" is the right instinct, but "important" is exactly the kind of word an LLM will interpret generously in whichever direction is convenient. Define it in code.

```
May assume, notify only:      impact == LOW  AND  area not critical for this profile
Must confirm before READY:    impact >= MEDIUM  OR  area is critical
Must ask, never assume:       problem, users
                              (anchoring risk too high — a wrong proposal here
                               corrupts everything downstream)
```

That last line is the important one and it's a deliberate exception to the propose-and-confirm default in §1.5. On most questions, giving the user something to react to is better than an open question. On *what problem are we solving* and *who is this for*, a confident wrong proposal is worse than silence, because the user will accept it and you'll plan the wrong product convincingly.

**Add an autonomy knob**, since "semi-opinionated" is a dial and different users will want different positions:

```yaml
autonomy: conservative | balanced | assertive   # default: balanced
```

It shifts one thing: the threshold in §3.2 Step C at which the agent assumes rather than asks. `conservative` assumes only LOW-impact non-critical items; `assertive` will assume MEDIUM in non-critical areas. It never changes the never-silent rule — assumptions are always recorded and surfaced regardless of setting.

**Build impact:** folded into S7.5 as an explicit threshold table rather than prompt prose.

### 6.5 Research needs real degradation states, not a try/except (from #5)

Agreed on the shape. Making it concrete:

```python
class ResearchProvider(Protocol):
    def available(self) -> bool: ...
    def research(self, question, context) -> ResearchResult: ...

# Three states, three behaviours:
AVAILABLE    → research, write RES-nnn with sources + researched_at
UNAVAILABLE  → item stays RESEARCH_REQUIRED,
               blocked_reason: "no_research_capability",
               owner flips to user, appears in open items,
               agent states plainly: "I can't research this here.
               From what I know: <degraded answer>. Worth verifying."
FAILED       → retry once, then treat as UNAVAILABLE and say which
               (a failed search and no search capability are different
                situations for the user)
```

**Gate rule — the one decision that matters here:** an unresearched `RESEARCH_REQUIRED` item blocks READY **only if it is also classified BLOCKING**. Otherwise it is a tracked open item and planning continues. Without this rule, one unavailable web search stalls the whole session.

**Stale findings.** Technical recommendations age badly — a database comparison from eight months ago is misleading, not merely old. Every `ResearchFinding` carries `researched_at`, and the status board flags findings older than 90 days as `STALE` when they underpin a decision that's still open.

**Build impact:** sub-step S9.5.

### 6.6 On deferring team collaboration — agreed, with one correction

Right call. Multi-user conflict resolution would double the v1 surface for no validation benefit.

One correction to the reasoning, though: **`created_by`/`updated_by` is necessary but nowhere near sufficient** for team support. The genuinely hard parts are:

1. **Concurrent writes** — the file-lock design in S2.1 assumes a single writer. Two sessions on one project will corrupt or block.
2. **Answer authority** — if the PM says "internal tool" and the engineer says "public launch," who wins? That's a product-policy question, not a technical one, and it has no obvious default.
3. **Async notification** — "decide later" reminders only work with a delivery channel.

What actually preserves the option is something you already have: **the append-only event log**. Every mutation already carries an actor and a timestamp, so multi-user becomes a question of adding identity and a merge policy on top of an existing history — not of reconstructing who did what. Adding the audit fields is still worth doing (it's free now), but the event log is what makes v2 tractable.

Recommendation: add `actor_id` and `actor_role` to the event envelope in S1.3, and note the single-writer assumption as an explicit constraint in the README so it isn't discovered accidentally.
