The flow

What happens between you typing an answer and the status board updating. Package names are the real folders under ppa/.

you · ppa/cli.py

ppa chat <project> starts a round. Seven commands exist: new, chat, status, history, why, force-ready, client-questions.

↓ opens project, reads ledger fresh
ppa/orchestrator

The outer loop. Checks preconditions, opens a transaction (txn.begin), runs one agent turn, then commits or aborts. A crash mid-turn leaves lines with no txn.commit, and every reader ignores them.

↓ agent turn
ppa/agents · model call

The Discovery agent works in a mode: intake (opening move), clarify (question engine), change, review. It can call the guidance and research subagents. This is the only place a model runs: interpretation, question generation, guidance, narration.

↓ every action is a tool call
ppa/tools · permissions

The dispatcher runs the permission gate first (right agent, right workflow state), then the five validation layers. A wrong-tool attempt is rejected before the tool body runs. External tools (Linear, Delivery) are stubs behind an approval gate.

↓ valid writes only
ppa/ledger

Appends to events.ndjson (append-only, secrets redacted before the write) plus audit.ndjson (who, which tool, which state). The project is its own local git repo.

↓ replay
ppa/engines + render

Coverage and readiness engines recompute from the log. The status board shows coverage, ledger counts, blockers and open items due. The readiness gate stays closed until every blocker clears, or you run force-ready and the skipped blockers are recorded.

When the answer is "I don't know"

It is classified, then routed: to research, to a client-owned open item (shows up in client-questions), or to an assumption. It never loops on the same question.

When a requirement changes

A new version is written, an impact report lists what it touches, and the readiness gate is recomputed. Old versions stay in history.

When something fails

Validation errors get a corrected retry. Transient errors retry up to 3 times. Permission and business errors are routed, not retried. Exhausted retries escalate with a concrete question.

How to test

Four layers, cheapest first. Run these from product_planning_agent/ after python -m venv .venv && .venv/Scripts/python.exe -m pip install -e ".[dev]".

1

Default suite · no model, no cost

Everything in tests/ except live-model tests. Covers ledger, engines, tools, permissions, validation, recovery, rendering, and the deterministic eval cases.

.venv/Scripts/python.exe -m pytest

expect about 909 passed, 1 skipped.

2

Wiring check

Confirms model and login wiring. No API key needed; it inherits your Claude Code login.

.venv/Scripts/python.exe -m ppa.cli doctor
3

Live-model tests · real calls, slow

Real Discovery turns. One multi-round session takes about 13 minutes, and the full 8-test matrix took about 1h31m. Run one test at a time. A single failure in a combined run is usually flaky; re-run it alone before calling it a regression.

.venv/Scripts/python.exe -m pytest -m live_model tests/eval/test_matrix.py::test_name
4

Scorecard · the one command for the eval matrix

python -m tests.eval.scorecard                 # 14 deterministic cases, fast
python -m tests.eval.scorecard --live          # + 4 live cases
python -m tests.eval.scorecard --matrix --fixture f06_detailed_k8s_audit_alerting --persona always_idk
python -m tests.eval.scorecard --save tests/eval/baseline.json
python -m tests.eval.scorecard --compare tests/eval/baseline.json

Use --compare after a prompt change to see the delta against the committed baseline.

What's left

The board is finished. These are the loose ends I found reading the README, cli.py and baseline.json. I did not run any tests for this review, so the test counts are from the handoff note and the baseline file.

gap

ppa report is still a stub

The command prints "not built yet" and points at T31, but T31 did not include it. It is the one CLI command that does nothing, and the README says it never got its own task. It is the natural next task: write the structured report to an output folder.

check

Recovery success rate is 50%

Baseline shows 0.5 against a "high" target. All 18 cases pass, so this is likely how recovery is counted across cases rather than a failing case, but I haven't traced which cases drag it down. Worth reading rubric.py and the per-case rows before treating it as healthy.

check

Invalid tool-call rate is 19.6%

Case 1's notes show five rejected manage_requirement calls with MISSING_COVERS_AREAS on the right tool. The agent is leaving out a required field and recovering. Fixing that in the prompt or tool description would lower the rate, and the scorecard's compare command would show it.

check

Coverage at the gate averages 78%

Questions-to-gate and coverage-at-gate are tracked, not targeted. An average under 100% suggests some matrix sessions ended before reaching full coverage, for example the adversarial or always_idk runs. Confirm which ones.

stub

Linear and Delivery are stubs

By design for v1. Case 12 passes against the stub. Real integration would need its own tasks, and the approval gate and scope_hash replay protection are already tested against the stubs.

risk

Live-model tests are not part of the routine run

The last full live_model run predates T35. Re-run it once, one test at a time, before trusting it. Repeated flakiness on combined runs is documented in NEXT_SESSION.md.

risk

Single writer only

The event log lock is a thread lock, not an OS file lock. Two ppa processes on one project can corrupt event IDs. Fine for a one-user CLI, a real gap for any shared use.
